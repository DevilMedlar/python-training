## Certificate chain diagnostic decision tree

Latest historical evidence: [GUI TLS report](<Archive/Medlar history/Avatar/Medlar-avatar-gui-tls-diagnostic-2026-10-07T15-12-42-238Z/report.txt>):7–17 records broadcaster-validation `CERTIFICATE_VERIFY_FAILED`, verification code20, with fresh GUI FAIL. 1. **No-network source/environment review first, after scoped access approval.** Record the exact interpreter used by GUI launcher/Core, Requests/OpenSSL/certifi versions, selected CA path and relevant proxy/CA configuration presence using sanitized metadata. Do not dump environment variables or credential-bearing proxy URLs. Check file existence/readability, expected certificate bundle source and system clock. Confirm process launch passes the intended nonsecret configuration, rather than assuming the terminal and GUI environments match.
2. **Branch on error stage.** A DNS/connect/timeout error is not certificate validation and not an authentication verdict. An SSL verification error requires chain/hostname/trust diagnosis. An HTTP response means TLS completed for that request; only then interpret 401/403/429/5xx separately. Never infer invalid tokens from SSL exceptions, absent status or IRC/API disagreement.
3. **With explicit network-probe permission, compare the same host and hostname with verification enabled.** Start with a credentialless bounded handshake/HTTP request to the actual affected endpoint host, record error class/code and verified chain metadata without headers/body/secrets. Compare the application trust source with a verified platform/default-context control in the same process environment. A credentialless 401 can establish TLS success only; it is not evidence about stored token validity. Do not make broad control-site sweeps.
4. **If only the application trust source fails:** verify CA-bundle selection, file permissions/integrity, stale override and known enterprise interception policy. If an organization proxy is involved, obtain the expected CA through the trusted administrator channel; do not trust a certificate merely because the failing connection supplied it. Propose the smallest application-scoped trust-source correction. Adding roots or changing system/enterprise security settings requires separate approval.
5. **If all verified clients fail:** investigate hostname, clock, missing intermediate/server chain, network/proxy policy and environment-specific trust failure. Preserve the evidence and escalate the correct infrastructure dependency. Do not replace tokens or downgrade to HTTP as a workaround.
6. **Validate a proposed correction:** synthetic nested-error tests first, then repeat the exact verified credentialless control under authorized network scope. Only with separate credential-use approval perform the minimum real validation needed. Log stage, result type, numeric HTTP status and safe verification code, never token, full request/response body or raw exception containing secrets.
7. **Return to GUI acceptance:** fresh Start must initialize PENDING and a fresh cursor; earlier OK/FAIL cannot carry over. A delayed synthetic fixture proves visible PENDING → actual result. In a fast live run the result may precede the first render, so record only states actually observed. Confirm IRC and broadcaster validation separately. Re-run only the bounded startup path initially; do not automatically send chat, change title/category or rerun all avatar stress tests.

Forbidden shortcuts: `verify=False`, unverified SSL contexts, hostname-check suppression, global SSL monkeypatches, indiscriminate root installation, clearing credentials on an SSL error, or disabling certificate checks in a diagnostic fixture that is later reused in production. A scoped trusted CA correction must be reversible to the prior application configuration, with no secret exposure. Root cause remains unresolved until evidence selects a branch.
